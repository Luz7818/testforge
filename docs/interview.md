# TestForge 面试手册

> 本手册是把项目"讲清楚、扛住追问"的操作手册：电梯稿 → STAR 故事 → 白板架构 → 追问 Q&A → 现场演示脚本。
> 建议配合 README（门面）与 docs/report.md（深度）使用；先读这两份再读本手册。

---

## 1. 电梯稿

### 30 秒版

> AI 生成单元测试最大的问题是"能通过但抓不住 Bug"——因为它优化的是覆盖率这种代理指标，而不是故障检出能力。Meta 今年在 FSE 上发表的 ACH 系统就是用变异测试解决这个问题。我做了一个开源复现加改进，叫 TestForge：LLM 生成候选测试，经过一个多信号质量门禁——必须在原代码上稳定通过、并且至少杀死一个既有测试杀不死的变异体——不达标就拒绝；再把"你的测试没抓到的种子 Bug"以 diff 形式反馈给模型迭代强化。18 个真实函数 × 5 个变体 × 双后端（真实 8B 模型两轮独立采样 + 确定性 Mock）的配对实验：真实模型让 10/18 个目标变异分数到 100%（pooled +12.7pp，p=0.0001），门禁把验收测试数砍半而质量不降。全流程可复现，CI 四格矩阵验证。

### 2 分钟版（按"痛点 → 机制 → 证据 → 工程"四段）

1. **痛点**：2026 年企业 AI 编程的头号抱怨是"产出几乎对但差一点"。在测试场景更隐蔽：LLM 针对当前代码写测试，测试天然倾向通过——断言弱、边界缺，覆盖率好看但抓不住 Bug。"测试通过"验证的是测试和代码互相一致，不是代码正确。
2. **机制**：TestForge 的核心是把"验收标准"换成变异体杀伤。生成 → 门禁（稳定通过 N 次 + 至少杀死一个存活变异体 + 可选覆盖增量）→ 反馈（存活变异体的最小语义 diff 回填 prompt）→ 迭代到分数平台期。每个被验收的测试都有独立证据：它杀死了哪个变异体。
3. **证据**：6 模块 × 18 函数基准，5 变体配对实验 × 双后端（真实 Qwen3-VL-8B + 确定性 Mock，共 180 格全部成功）。真实模型：+13.6pp（p=0.003）、10/18 目标变异分数达到 100%、门禁把验收测试从 23 个收敛到 11 个而检出力不降。门禁同时拒绝 Mock 生成器无法杀死的变异体对应的候选——系统不采纳无质量证据的测试。
4. **工程**：杀伤矩阵是 O(测试×变异体) 次执行，用进程池并行 + pytest -x 首败即停 + 只对存活变异体跑候选，把成本压到可用；prompt 缓存让重跑零成本；种子化保证可复现。

## 2. STAR 故事（行为面/项目深挖用）

- **S**：AI 编程工具普及后，团队发现 AI 生成的测试"看起来很美"——通过率 100%、覆盖率上涨，但线上 Bug 一样漏。Meta 在 FSE 2025 发表 ACH 系统承认并解决这个工业问题，但没有开源实现。
- **T**：我想验证这个思路能否在开源栈上端到端落地，并给出严格的量化评估，而不是一个 demo。
- **A**：设计了"生成 → 多信号门禁 → 变异体反馈"的闭环；自研 AST 变异引擎拿到测试×变异体杀伤矩阵（这是反馈和验收的数据基础）；设计了 5 变体配对实验和统计检验方案；为控制成本做了进程池并行、提前退出、变异体采样、prompt 缓存四件事。
- **R**：全管线 29 个自测通过；Mock 模式零成本复现全网格并暴露了系统的"诚实性"（门禁拒绝无法证明价值的测试）；DeepSeek 模式一键可跑全网格，预计成本 < ¥10；沉淀技术报告与可复现基准。

## 3. 白板架构讲解（5 分钟版）

画三列：**生成侧 / 判定侧 / 反馈侧**。

1. 生成侧：AST 静态分析提取签名/文档/既有测试 → 结构化 Prompt → LLM 一次给 K 个候选测试文件。
2. 判定侧（先讲门禁，再讲变异）：
   - 门禁三信号：稳定通过（flaky 检测）、可证伪（杀存活变异体）、覆盖增量（默认只报告，讨论为什么）；
   - 变异引擎：7 类算子 → 源码拼接 → 语法校验 → 分层采样；杀伤矩阵在临时目录里 pytest -x 执行，进程池并行。
3. 反馈侧：存活变异体 = B0 和已验收集合都杀不死的；把它们的语义 diff 塞进下一轮 prompt；贪心验收直到分数平台期。
4. 收尾：最终联合评估（所有变体同一把尺子）→ 报告 + 成本账单。

**主动暴露一个设计权衡**（展示判断力）：覆盖率增量为什么不强制——强化断言的测试可能不新增行却抓住覆盖行上从未校验的缺陷；强制会偏向"多跑代码"而不是"强断言"。所以做成开关，默认只报告。

## 4. 高频追问 Q&A

### LLM 工程

**Q：为什么不直接在 prompt 里说"写强一点的断言"？**
A：模糊指令对预言机质量没有可度量的杠杆。变异体 diff 是精确的教学信号——"你漏掉了 i+1→i+2 这种边界"，模型可以定向构造用例。这正是 Meta ACH 的核心机制。

**Q：成本怎么控制？一次实验要多少钱？**
A：四层：单响应携带 K 个候选；prompt 磁盘缓存（重跑零成本）；变异体分层采样上限；只对存活变异体执行候选测试。DeepSeek 全网格（18 目标 × 5 变体、几百次调用）预计 < ¥10；token 计数逐笔精确记账，价格只是可配的换算系数。

**Q：模型幻觉生成不可运行的测试怎么办？**
A：门禁第一关就是子进程沙箱里真实运行，语法/导入错误直接拒绝；API 模式还有一次带错误信息的修复重试。系统对幻觉的响应是"验证"而不是"信任"。

**Q：为什么 K 个候选一次生成而不是 K 次调用？**
A：省调用数与延迟；DeepSeek 对 n 参数支持不稳定，多候选通过标记分段在同一响应内表达。代价是单响应失败影响整批——用重试与缓存对冲。

### 测试理论

**Q：变异分数为什么比覆盖率好？**
A：覆盖率度量"代码被执行"，变异分数度量"执行结果被校验"。一个 `assert result is not None` 可以把覆盖率拉满，却杀不死任何改变返回值的变异体。覆盖率是必要条件不是充分条件。

**Q：等价变异体怎么办？**
A：理论上不可完全判定。工程上压缩近等价体：跳过错误消息字符串（只改消息不改契约）、docstring、注解；用 MS(covered) 辅助报告。残余影响是 MS 的下界偏置，所有变体共享同一偏置，配对比较仍然公平。

**Q：TIMEOUT 为什么算杀死？**
A：原代码终止而变异体挂起，测试观察到了行为改变；PIT 等工具同惯例。风险是测试自身死循环误判，但门禁要求测试先在原代码上稳定通过，排除了这种情况。

**Q：flaky 测试怎么处理？**
A：候选必须在原代码上连续通过 5 次（可配），任何一次失败即拒——把 flaky 拦在验收之前，而不是靠事后重试掩盖。

### 系统工程

**Q：O(测试×变异体) 的执行成本怎么落地？**
A：三个正交手段：只对 B0 未杀死的存活变异体执行候选（通常砍掉 40–70%）；pytest -x 首败即停；进程池并行 + 每次运行一次性临时目录隔离。18 目标网格在 8 核笔记本上约 1 小时，纯本地计算。

**Q：可复现性怎么保证？**
A：采样全用显式种子（crc32 而非内置 hash，规避 PYTHONHASHSEED 随机化——这是我真踩过的坑）；LLM 响应落盘缓存；实验每格增量落盘，崩溃可续跑；Mock 后端完全确定性。

**Q：扩展到 Java/Go 难在哪？**
A：三层可移植性：变异算子（各家语言都有对应实现，如 PIT）、测试执行协议（换成 JUnit/go test）、AST 分析（tree-sitter 或编译器前端）。架构与门禁逻辑不动。难点在变异执行的沙箱成本。

### 实验方法

**Q：你的结论统计上站得住吗？**
A：18 目标配对设计（每个目标跑全部 5 变体、同一变异体集、同一最终评估器），Wilcoxon 符号秩检验（正态近似 + 并列校正，n=18 已注明近似性质）+ bootstrap 95% CI 交叉验证；主指标 MS(all) 与辅指标 MS(covered) 同时报告。真实模型网格上 RQ1 的 p=0.0033、CI [+7.8, +19.7]，且 11 胜 0 负——不是靠均值撑起来的。

**Q：如果 B3 和 B1 提升不显著怎么办？**
A：这正是我在 8B 模型网格上实际得到的结果（B3-B1 = 0，18 目标全平局），我的解读有三层：第一，单次生成 3 候选已覆盖"易杀"变异体，反馈回路的边际收益取决于剩余存活体的语义难度；第二，全强度对照运行里反馈轮确实产出了杀死 5 个新变异体（含 Mock 无法杀死的算子变异）的验收测试——机制有效，是任务难度问题而非设计问题；第三，这给出了明确的实验改进方向：更大模型、更多候选、更多轮次。能够如实报告零增量并给出机制解释的实验系统，比只报告正向结果的系统更有工程价值。

**Q：Mock 模式的结果算数吗？**
A：不算效果结论，算机制验证。Mock 是捕获-重放式特征化测试生成器，能杀值/算子类变异体、杀不了需要语义理解的边界变异体——门禁对它同样严格。效果结论必须来自真实 LLM 运行，这也是我在报告里明确分开写的原因。

## 5. 可能的质疑与应对

| 质疑 | 应对 |
|---|---|
| "Meta 已经做了，你的价值是什么？" | 开源、可复现、带统计评估的端到端实现不存在；我把它的核心闭环变成任何人一行命令可跑的系统，并补了工程与实验方法论（杀伤矩阵归因、门禁信号组合、成本账目）。 |
| "变异测试太慢，实际没人用" | 正因为慢才需要工程：采样、并行、提前退出、只跑存活体。网格 1 小时是 8 核笔记本本地跑完的，且这是 CI 离线任务不是交互任务。 |
| "18 个函数太小了" | 它是方法论验证集，与 Meta 论文内部数据集不同源、不可比；扩展是量的问题不是质的问题——管线对目标函数无假设，manifest 加行即可。 |
| "为什么不直接用 mutmut" | 需要测试×变异体的**逐格归因**（每个测试杀死哪些变异体）来做门禁与反馈，mutmut 不暴露这个矩阵；自研 AST 引擎约 300 行、可测试、可采样控制，还顺带解决了消息字符串近等价体等噪声。 |

## 6. 现场演示脚本（5 分钟）

```bash
# ① 看目标与基准（10 秒）
python -m testforge.cli targets

# ② 跑一个完整目标，现场看门禁拒绝/验收（约 30 秒）
python -m testforge.cli run --target string_utils.truncate_with_ellipsis --variant B3 --mode mock
python -m testforge.cli report --results results/runs/string_utils.truncate_with_ellipsis__B3.json --out demo.md
# 打开 demo.md：变异体表逐格显示"谁杀死了谁"，门禁拒绝原因逐条可查

# ③ 展示"诚实性"案例（约 20 秒）
#    parse_csv_line：B0 已 93.8%，仅剩引号转义边界变异体，Mock 无法杀死 → 门禁全部拒绝
#    -> 讲清"特征化测试的极限"与"真实 LLM 反馈回路的机会"

# ④ 展示实验与统计（如已跑全网格）
#    results/exp_*/analysis.md + plots/ms_by_variant.png
```

## 7. 一句话收尾

> 这个项目对我最大的价值，是验证了一个范式：**把 LLM 从"生成器"变成"被验收的贡献者"**——每一个 AI 产出都要在系统里留下可证明的证据。这个范式不只在测试生成成立，放到代码评审、修复生成同样成立。
